# 主动接单与缺陷修复闭环

在启用独立调度并且用户授权周期启动时使用。解决两种实际缺口：就绪卡无人主动认领；审计发现只挂为验收阻塞而没有修复交付工单。本文约束角色行为；不是账号隔离、自动权限批准或硬实时服务。

## 接单必须有消费入口

分离后主 PM 维护需求、范围、验收和产品决定，第二 PM 提供指定产品材料。执行队列由调度独占；未安全交接的旧任务仍归原 writer。PM 忙碌不应成为已批准工作派发的前置条件。

`READY_FOR_DISPATCH` 本身构成调度待办，无须另一封 ASSIGN。产品范围明确即可进入调度；查明代码 owner、容量和独占目录是调度的工作。调度主动认领处理责任不等于扩大产品授权。

周期启动按实际工作量启停，不能默认常设高频轮询。上游阶段没有就绪输入且没有已认领的在途义务，下游job暂停。轻任务能在一次独立执行完成时，持久outbox后核实接收方安全空闲，仅一次原生启动；忙碌者在检查点自收，无需定时器。重任务、长工作包或多轮执行需要后续检查点时，才配置任务级临时跟进，建议15分钟或确切下一检查时间；不因正文长就自动建job，也不将每条消息变成定时任务。完成/取消、无待执行义务或纯外部等待无有益动作时暂停；有效等待记录owner/条件/确切复查时间。

READY和后续结果的生产者负责一次轻量接入启动；新重任务复用/恢复同一目标原job，不批量创建。文件本身不能唤醒被暂停角色，所以“空链暂停”和“新工作一次启动”必须成对实现。就绪后5分钟认领、10分钟派发或具体阻塞仍是目标，由直接启动和真实检查点支撑，不要求永久高频扫描来保证；平台排队与实际超期如实记录。

运行互斥、固定工具、游标和待办由本人维护；已有活动项在检查点续作，不创建第二writer，不重开任务。每轮优先真正新动作，读取必要增量；没有动作记录后退出，不在工具内循环等待。记录实际调用次数、耗时及工具可用的Token用量，未知不推算，不把字符数当Token。

工作包包含原 TASK、授权、固定输入、目标/非目标、允许范围、验收、依赖、唯一执行负责人、ledger_owner/authority_pointer、结果接收者和停止条件。已有开发负责人优先续作；每次代码写入仍检查真实目录、分支、容量及独占权。独立且已经批准的子范围可整体交一个开发负责人；不把待定法律文本或其他产品入口强行混入。

派发状态必须区分：`ready → dispatcher_claimed → assigned → developer_queued → developer_claimed → in_progress → pre_main → main`。接单凭接收者本人事件；实际行动凭分支/核实/实现或测试等真实证据。上游 completed、文件已写、会话创建或 queued 都不等于下游开始工作。

## 不打断忙碌角色，也不无限等空闲角色

正文始终由发送方本人 outbox 直达接收方本人扫描；调度只跟踪必要投递元数据，不成为审核/发布消息中转站。角色启动、当前项完成或阻塞、退出前扫描。busy 角色保留当前工作，到检查点再接后续项。

对已授权且需行动的消息，调度核对接收方下一扫描安排和任务重量。轻量接单、职责更新、一次补证或状态登记：已核实空闲安全点一次启动原message ID即可，不建周期job。busy不即时打断。重任务确需跨轮续作才登记临时原生跟进：目标本人scan原授权消息、继续原TASK；每目标最多一个job，记真实ID、父TASK/上游阶段、重量依据、原message ID、next_check、停用条件。正文保持原outbox，不中转、不新授权；轻通知不会因为缺扫描入口就变成2分钟轮询。

收件不是重任务的结束；若仍有已批准多轮执行义务，按实际下一检查点继续跟进。终态、取消、空链或纯外部等待时暂停；外部等待到确切复查时间再恢复。已有job按需复用，避免每个流水线阶段永久设timer。产品/源码/审核/发布下一阶段未就绪时，不预先启动下游定时器。

创建或触发 job 不是接收证明。平台不支持、触发失败、登记 owner 不明或接收方无能力时，记具体阻塞和恢复 owner；超期进入异常处理，不能永久标作“正常等待”。确知 busy、有效审批或资源窗口等待时，记录证据、解除 owner、条件及复查时间，继续其他就绪项。只读状态不证明 checkout 写权；不强制终止其他任务或新建第二个同任务开发者。

## Agent 发现问题也必须进入修复流程

```mermaid
flowchart LR
    A[审计 / 审查 / 任一 Agent 发现] --> F[本人 DEFECT_REPORT]
    F --> D[调度查重 / 唯一工单]
    D --> V[核实事实与批准基线]
    V -->|既定基线缺陷| DEV[原模块开发核实 / 修复 / 回归]
    V -->|需要新决定| P[产品 / 用户具体决策包]
    P --> DEV
    DEV --> PRE[pre-main]
    PRE --> R[专属审核晋级 main]
    R -->|需生产变更| M[管理核准 / 指定发布者 / 项目锁]
    M --> CHECK[实际复核后关闭生产缺陷]
```

发现者写自己的报告和 outbox，附稳定 finding_key、原父 TASK、环境、实际/预期行为、基线引用、影响、证据和唯一下一 owner。不写调度台账。调度本人查重：同环境/同缺陷链接原工单并追加新证据，不重复派发；同候选审查修改仍在原 TASK 闭环，独立交付范围才建关联修复工单。疑似项先核实，不将风险推断写成已发生数据泄露或篡改。

唯一工单至少含 finding_key、原父任务、source_report、authorization_ref、证实/疑似、环境与基线、范围/验收、核实人、execution_owner、ledger_owner、authority_pointer、状态、唯一 next_owner/next_action、各阶段证据和等待复查。记录按日期/类别/工单分页，当前执行真相只有一个 writer；其他人的笔记仅引用。

| 情况 | 处理责任与门禁 |
|---|---|
| 已批准基线内的确定 bug、测试补证、已有契约的实现纠偏 | 调度组织核实与完整开发包；开发自主修复和测试，专属审核晋级 main；不等 PM 再批准一次 |
| 是否为 bug 尚不明、缺确切证据 | 指定核实 owner 和时限，先核实；不假定需要人类，也不假定可修改 |
| 新产品范围、公共契约、数据模型、权限策略、不可逆动作 | 向相应产品/用户决策入口列明具体选项、影响和证据；只阻塞相关步骤 |
| 生产身份/凭据/授权、部署或远程资源写入 | 继续准备独立本地工程；真实执行仍走原用户范围、管理核准、指定执行者、窗口和项目锁 |

不能把“安全相关 bug”一律等同需要新安全策略；恢复已经批准的最小权限检查与新增权限方案是不同动作。也不能因为用户说修复便自行创建生产账号、调整共享权限或轮换凭据。

工程交付与生产缺陷分别收口：源码/配置、回归、pre-main、专属审查/main、管理核准、发布制品、实际运行身份和独立复核各有证据。仅配置问题不强造产品代码补丁；生产发现不能仅凭 main 已合或隔离测试通过关闭。故障回退恢复旧不安全身份时，服务可用与安全整改状态分别记录。被阻塞的生产切换不挡可先完成的本地核实/最小修复。

使用 [task_flow.py](../scripts/task_flow.py) 可只读检查缺陷分流、接单时间、按需启动和关闭证据缺项。去重同时比较finding_key与environment，environment须由owner核实为确切部署/实例标识；不同环境不串单，历史同键记录缺环境先核实，不推定同一或直接新建。输入由责任人核实；返回 ready 不是权限授予，返回 closed 仅表示引用字段齐备，实际证据和授权仍需独立核对。

验收同时检查规则、实际 timer ID/目标/状态和一次真实启动、本人接单/行动、完整缺陷工单及代码/配置流向；模拟测试和长期运行效果分开报告。无变化安静落记录；新严重失效、无法恢复的无人接手、完成或具体人类决定才通知。
