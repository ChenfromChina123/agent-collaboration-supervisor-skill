# 搭建、接管与安全交接

创建整套团队时读本引用；仅改进一条消息规则无需执行全部步骤。主管交付可运行的登记和规则，不靠创建会话数量证明完成。

用户采用持久待办时，同时读取[工作本协议](durable-workbooks.md)：主管指定各角色路径，各 Agent 本人 init 和维护日记；初始prompt要求在启动、当前项收口/阻塞及退出前只检查自己的邮件索引。新交接按[独立邮箱](mailbox-transport.md)提交正文、发送一次定向短通知；本人打开后才入待办，busy到安全点处理。旧outbox仅作有界迁移。存量忙碌角色保持 pending_adoption，到安全点或下次明确派单再接入。

## 1. 确认本次要建什么

从用户请求和当前项目中取得：目标、当前角色、文档权威入口、任务台账 writer、分支/评审规则、服务器边界、时区、是否需要周期监督。先查已授权的连接来源和登记；不能推断的关键权限才问用户，其余工作继续。

明确哪些动作已授权：创建/置顶哪些会话、给哪些对象发任务、写哪些独占本地路径、修改哪些项目规则、是否配置自动化。用户要求“建立团队”可以包含该团队所需的会话和规则准备，但不自动包含生产操作、替换既有负责人、归档历史或把私有资料公开。

建议按项目体量选择：

- 全套受控交付：主管 + 主 PM + 按需开发 + 最终审核 + 服务器管理 + 发布 + 独立审计。
- 当前无需服务器：保留审核与交付边界，服务器管理/发布登记为未启用，不空建服务器进程。
- 既有团队：只补真实缺口；角色已存在就引用真实 ID，不新建同名影子 owner。

本地 task root、主管观察根和 PM 协调根分别指定。规则可以同仓管理，但不同角色的运行状态不共写同一根目录。公开配置只放中性示例，实际内部身份、授权和日志留在本地或项目批准的位置。

## 2. 写出可审查的控制面

复用项目现有入口；缺少时在已授权范围内建立下列最小材料：

| 材料 | 权威内容 | 唯一维护者 |
|---|---|---|
| 角色登记 | role → 真实 thread ID、权限、受保护身份和权威版本 | 经项目认可的规则维护/审核流程 |
| 消息规则 | 允许路由、封套、终止/去重、安全例外、交付清单 | 同上 |
| PM 规则与协调根 | 任务/队列、主 PM owner、模块/目录归属、历史事件 | 当前主 PM |
| 主管规则与观察根 | 增量游标、覆盖、发现、委派和监督报告 | 当前主管 |
| 交付规则 | 开发集成线、正式源码线、审核、服务器核准和项目锁 | 原最终审核/管理/发布职责不变 |

配置样例的主线/集成线是 main/pre-main。项目采用其他分支或发布方式时映射到现有规则，不擅自创建新正式线或绕过现有门禁。正式发布只用经核对的正式线确切提交和对应制品；无服务器任务就不操作发布锁。

规则变更按项目文档索引、变更记录和决策要求回写。先核对真实目录、活跃使用者及 Git/worktree 状态；有并行写入或不确定独占时，保留原 checkout，在独占分支处理。只有用户/项目指定的审核者能批准生效，主管不能以“我是架构搭建者”自行取得 main 晋级权。

## 3. 创建与配置会话

使用平台的专用工具；不要通过手改应用内部数据库或会话元数据伪造身份。明确需要持久会话时才创建，保留用户默认模型，除非用户指定模型。用户未要求新会话且当前角色可完成任务时，不为展示架构而创建。

每个初始 prompt 包含：

```text
你的角色：{role}，本次项目：{project}。
用户目标与已授权范围：{scope}；本轮交付：{acceptance}。
权威入口：{rules_paths}，已核对版本：{policy_commit_or_unknown}。
实际本地根：{absolute_runtime_root}；UI 默认 cwd 是否共享：{yes_or_no}。
可读范围：{read_scope}；可写范围：{exclusive_write_scope_or_none}。
你不代行：{forbidden_responsibilities}。
当前父 TASK、候选、输入、依赖、停止条件：{packet_or_waiting_assignment}。
allowed_contacts：{authorized_contacts}；结果接收者：{business_owner}。
不要向创建者发初始化 ACK；用本会话完成结果供创建者读取。
只有本次工作需要真实交接时，按消息协议发送一次实际结果。
```

占位符只是编写模板；创建前填真实输入。若尚无独立任务，写 waiting_assignment，只初始化已授权职责，不编造产品工作。共享 UI cwd 不等于写入权；所有实际文件/Git 操作显式指定授权目录。

创建后取得真实 ID，先登记再按职责置顶，核对工具结果。如果工具返回异步 operation/client ID，按工具状态完成解析后才当正式 thread ID 使用。一次有界状态等待核实开始/完成/需用户操作；无变化不密集轮询。

**置顶验收**：所有非代码开发角色均已置顶，开发默认不置顶；原生无侧栏子代理记不适用。不要为了调整排序而取消用户原有置顶，也不批量改名/归档旧会话。工具未提供置顶能力时保留创建结果，说明需要用户完成的精确一步，不声称已置顶。

只有当用户授权了对应跨会话联系时才发送规则/交接消息。一次授权的政策告知无需回执；新会话把规则入口放在初始 prompt，避免常驻广播。创建工具若已把 prompt 送达，不再重复发送同一任务。

## 4. 本地运行根初始化

在确认最终登记、本角色真实 ID 和独占路径后，首次 owner 文件用原子排他创建（如 O_EXCL）。存在未知 owner 就保留，核对是否为同一真实路径及活跃 writer；不能覆盖、删锁或换路径绕过归属。

owner 建议记录：role、thread_id、真实路径、policy commit、状态和时间。首次运行先追加 started，再取得自己的本地运行互斥；主管运行锁不等于生产项目锁。状态原子替换，原始事件追加不覆盖。失败也保存 finished 与 unknown 原因；重叠运行记 skipped_overlap，不重复巡检。

主管的游标/覆盖日志不接管 PM 台账。助手输出使用单独指定目录，不共写主管 owner、全局任务或产品 checkout。临时工具创建状态不明时先查实际结果，保留记录，不自动再创建一份团队。

## 5. 代际继任与退出

可配置 PM/开发会话累计独立 TASK 上限，例如每代 10 项，在第 11 项前 fresh 继任；这只是可选治理参数，只有用户或现行规则批准后执行。按唯一 TASK-ID 集合累计，排队/已完成都计入，查询/重试/补证不另计。历史数量不明保留 unknown，不凭会话标题猜 0。

继任先保护原始任务与现场，前任到安全点停写，再核对真实目录、分支、未提交/未跟踪/必要 ignored 内容、写进程、验收服务和工具托管归属。以受支持方式更新唯一 writer 后，继任才可写。创建成功不等于拥有原目录；工具归属拒绝不能用手工路径或内部 metadata 绕过。

最终审核、服务器管理、发布、审计、主管等受保护角色不自动轮换；变更由用户明确指定并登记。继任不延长旧许可窗口，不继承未授予的发布权。归档/回收另核对任务终态、主线集成、现场保护、未结自动化和活跃使用者；最近没有提交不是可删证据。

暂停主管时仅暂停自己的自动化，保存游标、发现和未结委派并交接，不改其他角色的定时任务，不删历史。任务归档可能连带回收托管工作树，先核对平台实际行为和目录使用者。

## 6. 搭建完成证据

交付角色表、真实会话链接、置顶结果、规则路径/版本、独占根/owner、任务与消息最小样例、自动化实际状态及验收结论。区分：草案写好、已评审生效、会话配置成功、单轮运行成功、长期效率改善。

规则推演至少覆盖：第二 PM 不写全局台账、无动作消息不回复、候选变化需重新审核、无核准不得服务器写入、两个 writer 不能同目录、创建不明不能重复建助手，以及非开发角色置顶。推演只证明规约能给出决定，不证明远端系统强制执行。

新增派单的原生标题追加、读回、在途容量和未知历史处理按[标题与容量](task-title-and-capacity.md)；仅用户明确批准的身份可有命名例外，不据标题解析累计。
