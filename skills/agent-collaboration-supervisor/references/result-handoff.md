# 阻塞、结果与交接收口

执行者必须在真实阻塞或阶段结束的本次收口中主动反馈，不能等主管巡检或用户追问。发给用户的聊天答复、产物文件和本人completed事件都不能代替给原下一负责人的结果邮件。

- **阻塞**：本人记录原因、证据、受影响范围、仍可继续的工作、唯一解除owner和下一动作；向原执行台账owner发送BLOCKED邮件。缺人类决定才请求具体人类输入。工具取证失败与产品失败分开；缺入口先核对原工作包、已有授权入口和受支持浏览器能力，不能跳过可独立推进的部分。
- **阶段完成**：本人提交RESULT，写明实际完成范围、证据、未完成/unknown及下一owner。完整报告按原包直达指定接收者；调度只收原约定的执行状态/指针，不复制正文。阶段完成不关闭父产品、未验收生产问题或其他owner职责。
- **交接状态**：执行状态和handoff状态分开。按事实记pending_result、stored、notice_deferred、notice_sent、opened、owner_queued及delivery_unknown。需要后续动作时，只有接收者本人的入账/接单才证明责任接管；发送者不持续轮询等待，也不发聊天ACK。无动作信息不唤醒。
- **通知**：先存完整邮件，随后在安全空闲点一次短通知。busy时记录延迟原因/原ID，收件方在自己的检查点收取；退出前保留未通知指针，不能假称已交付或重投原正文。用户可见答复简述实际结果、已交给谁/真实交接状态、下一步或阻碍。

主管仅按用户选择的低频节奏旁路核对；普通场景可每日一次。执行者及原台账owner承担当次主动交接，不能把每日监督当作派单/补反馈触发器。现有脚本没有客户端强制结束钩子；这是角色自查与原执行台账的验收门槛，不冒充平台自动强制。
