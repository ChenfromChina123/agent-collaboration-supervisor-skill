# 派单、标题追加与任务容量

适用于用户要求按新增任务追加会话标题，或已有证据表明派单/命名/累计任务登记漏项的项目。具体分隔符、例外身份和每代上限必须来自用户或项目现行规则，不把一个项目的例外变成所有项目/调度者的默认豁免。

## 一个任务集合，两类证据

标题追加、保留任务历史与任务上限是不同规则。上限只约束用户明确指定的角色；代码开发的10项示例不适用于PM、调度等非开发角色。用户明确PM无上限时，继续保留真实任务记录但不应用容量门槛或自动换代。角色范围纠偏后，旧会话和新产物按单writer安全交回，不能取消业务、重投派单或由主管共写台账。

同一task_id的执行台账owner负责该次派单元数据和原生命名；旧任务未交接时仍归原writer。先核对真实执行者、历史唯一TASK集合、在途派单保留位、当前队列、独占真实目录/分支及有效授权，再发送完整邮件。标题、斜杠数、Git提交、idle或日期都不是任务累计来源。

| 工作 | 唯一TASK/累计处理 |
|---|---|
| 新独立目标、独立交付的子执行任务 | 保留父TASK链接；实际独立TASK计一次 |
| 独立只读调查、缺陷修复、治理交付 | 有独立验收目标和实际独立TASK时计一次；不因“不新增产品范围”排除 |
| 同TASK补充、续作、补证、重试、命令、阶段、协议接入子步骤 | 关联原TASK，不按消息或处理项另计独立TASK |
| queued、已完成、取消后的已接收TASK | 已接收历史仍保留，不因结束、改名或新一天清零 |
| 尚未确认接收的在途独立派单 | 作为reserved_task_ids占容量；接收后转入accepted集合，不重复计数 |

容量按accepted与reserved的唯一并集核对，不能在前一单尚未接收时又把同一个剩余名额派给另一单。取消/投递失败只有实际核实未接收且安全撤回后才释放保留位；未知投递仍占位。上限及安全继任仅适用于项目已批准的角色/规则，不能因此自动轮换受保护审核、管理、发布等角色。

原始计数为null或更早历史缺失时，保留lifetime_task_count=unknown，可登记known_task_ids、known_minimum和history_coverage及出处。它们不能冒充完整累计。新独立派单前核实未知容量，或按已有明确授权的安全继任规则处理，不猜0、重置计数或抢占旧writer。原PM记录只读，分离调度只能修复自己持有的sessions/执行元数据。

## 标题追加与实际读回

当用户选择追加样式时，先读取原生当前完整标题，再保留原文并用约定分隔符追加简短任务名，例如`原完整标题/新任务简称`。同TASK补充/重试不重复追加。已核实的用户例外按真实actor ID登记；命名豁免不豁免计数、认领、权限或其他协作规则。

原生当前标题与台账缓存不同，先保留用户/其他合法owner的新改动，再判断原TASK是否已有title_task_map。不能把整段旧标题替换成短名、按标题长度裁掉完成历史，或把斜杠片段数当累计。用户未授权历史裁剪时保留完整标题；平台长度限制导致失败则记录阻塞和下一owner，不静默裁剪。平台无原子条件更新时，不宣称避免了所有并发改名竞争。

一次派单应形成以下证据链：

1. 原TASK与完整工作包、实际执行者、容量/保留位、唯一目录/分支及原writer核对。
2. 独立邮件提交保留原message_id；按[邮件协议](mailbox-transport.md)定向短通知、本人收件/认领和实际动作。
3. 用受支持原生命名工具追加标题，再通过原生查询读回真实标题。只设置成功但没有读回不能记verified。
4. 在派单owner本人记录TASK、actor、命名前后完整值、工具结果、readback、时间与title_task_map，不代写执行者工作本。

命名和业务交付分别记录。标题失败写rename_pending或metadata_incomplete，不丢弃原ASSIGN、不重发业务邮件、不重建TASK、不撤销已批准开发。补偿只修复命名/登记：重新读当前标题、合并用户新改动、确认原TASK未已追加后再修复。没有新业务动作不唤醒执行者，不发ACK或加定时器。派单owner不能用“已命名”代替本人接单/动作，也不能把metadata_incomplete报成完整派单闭环。

## 历史补齐

只按明确范围读取原ASSIGN/HANDOFF、原始唯一TASK和本人sessions，记录覆盖边界与未知；不扫描所有聊天或根据标题猜历史。标题遗漏修复和任务集合修复分开给证据，保留原业务TASK、许可、取消、计数和交接事实。登记缺失由对应writer本人补齐；主管给固定缺口/规则并核对结果，不共写主PM/调度台账。

小范围验收检查：同TASK只追加一次；新独立TASK追加一次；例外身份只豁免自己；标题读回与实际值一致；改名失败保留原邮件/任务；未知累计不变成0；在途名额不重复分配。静态规则、历史修复及下一次真实派单采用分别取证。
