# 增量监督与受限并行

主管旁路取证，业务流程继续走各自 owner。读取本引用不授权定时任务、发消息或创建助手。

采用[工作本协议](durable-workbooks.md)后，主管每轮先本人 scan，结束前再 scan；“结果交 owner”改为发送方自己的 outbox，接收方自己拉取。巡检只读工作本 owner、事件序号、待扫/已认领/阻塞数量和更新时间，不代写他人记录。位置已登记而本人尚未 init/扫描的角色标 pending_adoption；不能把发送方发布当成对方已接收。

## 监督运行

只有用户要求周期监督时，使用平台原生调度；先查是否已有相同计划，更新已有项避免重复。明确目标会话、时区、触发周期与通知条件，可采用以下建议配置：

- 一项 30 分钟增量触发；每天指定本地时间（如 09:00）之后的首轮，汇总前一本地自然日，不再建第二个日报定时器。
- 每轮最多详细读取 8 个变化/活跃会话，按风险、新事件和最久未覆盖者轮转；其余只统计元数据和缺口。
- 无变化或无可执行新发现保持安静；重要新问题、恢复/完成或需用户决定时才通知。
- 首轮不足一日标 partial，不倒填初始化前历史。调度尚未激活就如实记 paused/not_configured，不声称监控已运行。

这些数值是可选默认值；沿用项目已批准的配置。没有周期授权时，完成一次用户请求的有界观察即可，不为跟进方便自行设置计划。

开始先核对权威角色登记、自己的 owner 和运行锁，追加 started。只读全局任务、事件、会话/模块名册和新增消息元数据；需要事实才读取必要轮次/证据，不反复导出完整聊天。优先紧凑状态快照；必须读取会话时，在工具编排层提取状态、必要消息、游标和耗时，过滤初始 preview、命令正文、推理和大输出，关闭 includeOutputs 不保证返回包很小。保存增量状态游标，与读取历史用的向后分页游标分开；截断或未分页范围不算覆盖。

## 日志布局与真实覆盖

主管独占运行根可采用：

```text
owner.json
state/cursors.json
state/coverage.json
runs/YYYY/MM/RUN-ID/started.json
runs/YYYY/MM/RUN-ID/finished.json
runs/YYYY/MM/RUN-ID/finished.md
findings/FINDING-ID.json
delegations/DELEGATION-ID.json
reports/YYYY-MM-DD.json
reports/YYYY-MM-DD.md
```

日志只含脱敏摘要和证据指针；不存令牌、密码、数据库转储、完整消息导出或用户业务数据。终态包含来源版本、读取区间、覆盖/缺口、样本量、发现、消息/工具引用、错误与下一动作。中断、权限不足和工具失败保留 unknown。单个失败不能清零游标或改写成功历史；重复运行复用完整窗口证据。

coverage 分别记录已知 inventory、可读项、元数据覆盖、详细覆盖、各会话最近时间/区间及缺测原因。未知名册不当空团队；8 个详细会话不代表全项目全覆盖。日报基于真实样本窗口，长期效果必须有跨期可比证据。

## 指标与卡点判定

| 指标 | 合理口径 | 不可推断 |
|---|---|---|
| 交接响应 | 已核实投递到首次实际动作 | ACK、工具投递成功不算完成工作 |
| 阶段时间 | 同 TASK/候选的进入、开始、结束 | 未完阶段无结束时间，不当零耗时 |
| 等待 | 内部排队、外部输入/核准、资源窗口分别记 | 已知批准等待不叫执行故障 |
| 消息效率 | 具体 message_id/顺序/候选/正文与允许路由 | 相同正文可能是必要纠正或安全通知，先核范围 |
| 工具耗时 | 真实 start/end 或工具 duration，记录样本 | 无数据时不能推断模型排队、token、网络或磁盘原因 |
| 分位数/趋势 | 相同口径原始样本和覆盖范围 | 不平均每日 p95，不把少量样本称稳定 p95 |
| 并行就绪 | 固定输入、独立范围、owner、结果路径和权限 | 缺材料、idle 或超时不代表可用容量 |

可采用两轮规则：同一可执行任务连续两轮无实际进展、且没有已知外部/资源等待，才记待调查卡点；一次 SUPERVISION_FINDING 给原业务 owner，含证据、suspected/confirmed、解除条件和唯一下一动作。它不授权接管、重启或自动批准。约定截止/窗口风险按既有协议立即处理，不机械等待两轮。

同一发现保留 finding_id，记录首次/最近观察与通知 message_id；无新证据不再通知。恢复要有真实结果，聊天结束/未读消失不算恢复。主管只负责自己的停写，必要安全风险交管理者/指定执行者处理，不越权实施生产恢复。

## 委派就绪包

业务 owner（主 PM 或最终审核）提供：

```text
PARALLEL_REQUEST
parent_task_id: 已授权的现有任务
business_owner: 对最终结果负责的真实角色/ID
goal_and_acceptance: 原范围与验收
candidate_or_question: 确切 SHA 或明确待分析问题
scope / non_goals: 可独立分项与排除项
inputs_and_dependencies: 固定输入及证据指针
access: 允许读取、独占输出；禁止的写入
result_recipient: 接收报告的人
allowed_contacts: 本任务允许的联系对象
deadline_and_stop: 截止、停止条件和许可边界
```

主管不自己编造产品需求来填满空位。缺项一次列齐，不先 ACK 再追问。已知同候选同范围有人做时复用结果；同一候选可以按不同专题并行，避免两人重复全量审核。

## 名额与生命周期

沿用用户批准的总限额，建议额外助手合计最多 2 名，并受平台实际槽位限制。额外持久 PM/审核协作者参与委派时也计入；不能按助手类别、工作树或改名绕过限额。

在主管自己的本地互斥内原子预留名额，记录 delegation_id、父 TASK、业务 owner、候选/范围、helper 真实 ID、联系人、独占输出与停止条件。准备/创建不明/执行/结果待核对都占名额。创建失败先查实际结果；creation_unknown 未解决前不补建同名助手。业务 owner 核对结果或确认取消后才释放。

优先短期原生子代理；只有确需持久会话且获准时创建 fresh 会话。若当前工具/用户约束不允许委派，完成方案和就绪检查并报告能力边界。助手不能递归创建助手或子主管，也不能因受委派而获得产品目录、主台账或服务器写权限。

主管一次把助手身份/输出交请求 owner。助手结果直接交业务 owner，由 owner 集中向开发提出问题并作最终决定。若原生工具只回创建者，明确工具限制，由主管合并一次结果转交业务 owner；不声称已直达，不引入额外 ACK。没有实际报告的工具完成标记不当业务结论。

审核助手只读安全/API、UI/兼容、证据一致性等指定分项；不能批准候选或改代码补过门禁。PM 助手只读授权任务元数据、准备验收和依赖材料；只有主 PM 指定双方/问题/期限后才询证，不读产品私有实现、不共写全局台账。必须改源码时退回原开发正常流程。

## 串行门禁保留

并行分析不能并行最终批准、写同一全局台账、写同一目录/分支或绕过服务器管理。所有服务器写入，包括远程测试上传/创建/构建/启停/清理，仍需具体用户范围、管理核准、指定执行者和项目锁；正式发布还需已审正式线制品。核准窗口和预算不因并行自动延长/复制。

本地运行锁、委派名额锁、资源准入锁、生产项目锁用途不同，不互相替代。锁龄、超时、idle 或未收到消息均不足以删除锁或推断旧 writer 已停。
